# 04-评估与质量证据(面试拷打)

> 一句话: 这一篇拷"你怎么知道它变好了" —— 指标口径、噪声带、测试集来源与盲区, 以及"别把噪声当改进"的纪律。
> 用法: 先自己答, 再对照"答题骨架"; 深挖追问答不上来就回 [讲解 05 篇](../rag_v01/05-质量检验策略与方法.md) / [讲解 06 篇](../rag_v01/06-评估工程实现.md)。
> 这一篇是**最容易露馅**的地方: 说不出噪声带的来历、或者拿 0.01 的差异当结论, 面试官立刻能判断你真跑过还是只跑过 Hello World。

## Q1. 你怎么评估这个 RAG 系统?(基础)

**答题骨架**
分四层证据, 每层能证明的东西不一样: ① 纯函数单测(切分、清洗、RRF 排序与去重)证明逻辑对; ② fake 集成(替换掉 Milvus 与 LLM, 但用真实 schema 对象断言)证明段落之间拼装对; ③ 真机冒烟(建表幂等、分词对齐、跨模态相似度、重启持久性)证明真环境能用; ④ ragas 四指标 + 新旧双跑证明**效果**真的好。分开的理由是: 前三层能告诉我"哪里坏了", 第四层才能回答"值不值得换"。

**深挖追问**
- "为什么不用 ragas 一把梭?" → 它慢、贵、且只能给一个均分; 逻辑错误应该在秒级的单测里就被抓住。
- "两层测试分别多少?" → `src/rag_v01/tests/` 203 项(含真 Milvus 相关), 主线 `tests/` 201 项; 全套 404 项, 2 项失败是远程沙箱不可达的外部依赖。
- "跑一次全量评估多少钱/多久?" → 40 题约 32 分钟, 生成与判分都是真 API 调用; 所以我用 `--limit 5` 先试跑看账单。

**证据锚点**: 全套件 404 项(402 passed / 2 failed)/ `eval_reports/` 四份报告 / [讲解 05 篇](../rag_v01/05-质量检验策略与方法.md) §一。

**常见错误答法**: 只说"我用 ragas 评了, 分数不错"。没有分层、没有成本意识, 听起来像跑了个 demo。

## Q2. ragas 的四个指标各自衡量什么?(进阶)

**答题骨架**
两个看检索、两个看生成。`context_precision` 是**检索回来的材料里有多少是相关的**(逐条判相关, 算比例); `context_recall` 是**参考答案的要点有没有被检索覆盖到**; `faithfulness` 是**回答里的论断能不能被上下文支持**(测幻觉); `answer_relevancy` 是**回答是否切题** —— 它的算法比较特别: 让模型根据回答**反推问题**, 再看反推的问题和真实问题是否一致。所以前两个变了就是检索的问题, 后两个变了是生成或判分的问题。

**深挖追问**
- "反推问题为什么能测相关度?" → 如果回答答的是别的方向, 反推出的问题就会偏离原问题。它有个已知弱点: 需要模型生成 3 个反向问题, 实测经常只返 1 个, 稳定性一般。
- "NaN 是怎么来的?" → 单题判分失败(比如输出被截断、格式不合), 我设了 `raise_exceptions=False`, 失败就留 NaN 继续跑; 均值忽略 NaN, 所以 NaN 多的那一轮天然"看起来更好", 我把 NaN 题目名单写进报告 meta 用来防这个错觉。
- "四指标有什么内在矛盾?" → 有的: 保守的兜底话术(资料不足就说不知道)faithfulness 满分、answer_relevancy 为 0; 所以不能单看一个指标。

**证据锚点**: `evaluation.py` 的 `METRIC_ALIASES`(49-54)/ `build_metrics`(237-245)/ `ragas_evaluate` 里的 `ragas.evaluate`(:311, 判分请求发远程 judge)/ `_mean` 全 NaN 返回 `None`(353-356)/ 报告 meta 的 NaN 名单。

**常见错误答法**: 把 `context_precision` 说成"检索准确率"、"recall 越高越好"。要说清 precision 看**材料里有用的比例**、recall 看**该找的有没有找到**。

## Q3. 评估时 contexts 用的是父块还是子块?为什么?(进阶)

**答题骨架**
用**父块**。三个理由: 一是与线上同源 —— 线上喂给模型的也是父块, 评估口径跟它一致才代表真实效果; 二是 `context_precision` / `context_recall` 评价的是"模型看到的材料好不好", 那材料就是父块; 三是与工具返回的 content 口径同源, 于是"检索质量"和"子智能体看到的上下文"不会再各说各话。另外我保持 **RRF 名次顺序、不排序不去重**, 因为顺序本身就是信息(相关材料排第几), 重排会让 precision 读数失真。

**深挖追问**
- "用子块评会怎样?" → 会高估: 子块聚焦, 相关度高; 但线上给模型的是父块, 读数就成了"另一个系统的成绩"。
- "为什么不去重?" → 同父的多个命中子块反映的是"这个父块被多个角度命中", 是真实信号; 去重会掩盖检索深度。
- "怎么知道相关块排第几?" → 报告里的 `debug` 字段记了每题命中的两路名次与 `rrf_rank`。

**证据锚点**: `evaluation.py:168-182`(`make_sample`, 注释写明 contexts 取 `parent_text` 且保持名次)/ `debug_of`(122-139)/ 报告 meta 的 `contexts_source="parent_text"`。

**常见错误答法**: 说"用子块评更精确" —— 精确但**不代表线上**, 这是评估口径最容易搞错的一处。

## Q4. 你怎么证明这次改动真的有效?(深水, 最重要的一题)

**答题骨架**
先证明**评测本身可复现**, 再谈改动。我做过两组实验: 第一组, 把同一份中间产物(输入完全固定)只重跑评估, 结果是**检索侧两个指标 Δ=0**, 但 **faithfulness Δ=0.20、answer_relevancy Δ=0.09** —— 说明噪声来自 LLM 两端(生成 + 判分), 不来自检索。第二组, 40 题全量重跑(生成也重跑), 检索侧 Δ≤0.003 而生成侧 Δ0.028~0.048。由此我定下判读纪律: **差异小于 0.1 不下结论**; 要测"参数改动的效果", 就用「仅评估」入口固定同一份中间产物, 或者按 (question, contexts) 缓存生成结果; 并且优先看**逐题变化**(比如候选深度 20→50 时 20 题里 11 题 top-5 变了)而不是均值微差。

**深挖追问**
- "那你怎么敢说新内核比旧的好?" → 40 题同语料同生成器同 judge 的双跑里, 上下文精度从 0.6896 到 0.8958(**+0.206**), 这是唯一明确超出噪声带的一项; 其余三项方向为正但落在噪声里, 我在报告和文档里都标了"不足以单独下结论"。
- "为什么判分侧噪声这么大?" → judge 是 LLM, 它对同一份输入给出不同判断; `answer_relevancy` 还要模型生成反向问题, 更不稳。
- "有没有办法降低噪声?" → 多轮取均值、固定输入、扩大题量; 代价是钱与时间, 目前题量只有 40。

**证据锚点**: `eval_rag_v01_rerun_20260922-180435.md`(固定输入双评 / 全量重跑)/ `eval_tools_rag_v1_20260922-203552.md`(新旧双跑, 末尾自动并排表)/ 噪声带数字见 [讲解 05 篇](../rag_v01/05-质量检验策略与方法.md) §5.2。

**常见错误答法**: "我改了之后指标涨了 0.03, 说明有效"。0.03 完全在噪声内 —— 这么答基本等于承认没做过复现性实验。

## Q5. ragas 可信吗?它的局限是什么?(深水)

**答题骨架**
它有用但不该被当成"真理机": 一是**判分靠 LLM**, 同一输入会抖(faithfulness 抖 0.20), 所以它适合看**量级差异**而不是小数点; 二是**指标口径要自己校正** —— 比如参考答案是短语时 `context_recall` 偏乐观; 三是**它只测"检索 + 生成"这一条链**, 测不到分块质量、增量更新、多轮对话这些; 四是它需要额外依赖环境(我为此开了独立的 uv 项目, 因为它和主项目的 rich 版本互斥)。所以我的做法是: 把 ragas 当**回归参照**, 每次改动对着同一份测试集比, 同时用单测与真机验证补它覆盖不到的地方。

**深挖追问**
- "为什么独立环境?" → ragas 0.4 经 instructor 要求 `rich<15`, 主项目是 `rich>=15`; 我用环境级 `override-dependencies` 只在评估环境放宽, 主环境的锁文件一个字节没动。还实测必须钉 `langchain-community<0.4`, 否则 import 直接崩。
- "还有哪些坑?" → 嵌入适配器要同时实现新旧两套方法名(基类要 `embed_text`, 内部却调 `embed_query`); `total_tokens`/`total_cost` 是**方法**, 且 `total_cost()` 在没配 token 解析器时会抛 —— 我第一轮全量评估就是跑到最后崩在这上面, 导致半小时的评估报告落不了盘。
- "怎么防止同类事故?" → 报告生成路径上每个字段都按"可能抛错"处理(`_value_of` 容错), 因为报告是评估的唯一产物。

**证据锚点**: `evaluation.py` 的 `_value_of`(331-343)/ `eval/` 的 `override-dependencies` / [讲解 06 篇](../rag_v01/06-评估工程实现.md) §五八个坑。

**常见错误答法**: 说"ragas 是业界标准所以可信"。要能说出它的**噪声**与**覆盖边界**。

## Q6. 你的测试集怎么来的?有什么盲区?(进阶)

**答题骨架**
用的是 DuReader-Robust 公开镜像(学术研究许可), 从 14520 段里抽 500 段当语料、40 条当测试题。好处是每条题自带参考答案与 `answer_start` 偏移, 所以"参考答案确实在源段落里"能**自动校验** —— 省掉了自己出题 + 人工校对一整道工序。盲区有三个我主动说明: ① 语料是一段一文件、段落中位 215 字, 所以 **1 文档 = 1 父块**, 父子分块的"多子块/跨页/同父去重"能力**没有被评估覆盖**(这部分靠 21 项单测 + 15 页真 pdf 人工核对); ② 参考答案是短语, `context_recall` 偏乐观; ③ 语料是资讯问答, 不是技术文档, 长文档层级结构没被覆盖。

**深挖追问**
- "为什么不用 LLM 出题?" → 省工序: 现成的答案与出处, 且可自动验证出处正确; LLM 出题还得人工审一遍。
- "40 题够吗?" → 对"量级差异"够, 对"小数点级差异"不够; 这也是我不敢下小结论的原因之一。
- "怎么补盲区?" → 真 pdf 做人工核对(15 页讲义、156 条目全部带页码), 单测覆盖边界分支。**不假装评估覆盖了它。**

**证据锚点**: `data/eval_qa_v1.jsonl`(40 题, sha256[:16] `4136f7b616bc6041`)/ [rag_0.1/06 篇 §3.2](../../../new_module/rag_0.1/06-ragas评估.md)/ 真 pdf 实测记录见 [rag_0.1/TODO](../../../new_module/rag_0.1/TODO.md)。

**常见错误答法**: 说"测试集是我自己写的 20 个问题"。要说出来源、许可、自动校验机制与**盲区** —— 盲区这一条最能体现诚实。

## Q7. 如果指标变差了, 你的排查顺序是什么?(实战)

**答题骨架**
先分**是检索还是生成**: `context_precision` / `context_recall` 掉了 → 检索侧; `faithfulness` / `answer_relevancy` 掉了 → 生成或判分侧。检索侧再分两路: 看 `debug` 里的两路名次, 某一路专属的命中丢了就是那一路的问题(向量路查维度与 embedder 是否换过、稀疏路查 analyzer 与停用词)。生成侧则先排除**判分噪声** —— 把同一份中间产物再评一遍, 如果两轮差 0.1 以上, 那"变差"可能只是 judge 抽签。再之后看是不是**输入变了**(上下文条数/长度、截断闸门), 最后才怀疑提示词与模型版本。

**深挖追问**
- "怎么快速排除判分噪声?" → 用 `--samples` 只评不检索, 固定输入评两遍看差异。
- "检索侧的坑有哪些典型?" → 换过 embedder 或维度(旧向量作废)、analyzer 词表改过但没重灌、超长子块被跳过、图片块退化成文本。
- "改动了但没有重灌, 会怎样?" → 分块与 analyzer 类改动**必须重灌**才生效; 只改查询期参数(候选深度、`ef`)不用重灌。

**证据锚点**: [讲解 03 篇](../rag_v01/03-检索侧全链路.md) §九排障表 / [讲解 08 篇](../rag_v01/08-调参与容量手册.md) §四(重灌条件)/ [讲解 05 篇](../rag_v01/05-质量检验策略与方法.md) §5.1(指标→环节映射)。

**常见错误答法**: 直接怀疑模型或提示词。**先分清环节**, 再花钱。
