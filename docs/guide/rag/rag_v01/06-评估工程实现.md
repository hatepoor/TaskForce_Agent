# 06-评估工程实现

> 一句话: 评估是**两段式**的 —— 先把"检索 + 最简生成"落成中间产物 jsonl, 再拿这份 jsonl 喂 ragas; 分开的理由是 ragas 装在独立环境里, 而产出 jsonl 的那一半完全不依赖它。
> 对应实现: `src/rag_v01/evaluation.py`(~580 行) + `eval/`(独立 uv 项目) + `src/rag_v01/cli.py` 的 `evaluate` 子命令
> 前置: [05-质量检验策略与方法](./05-质量检验策略与方法.md)(讲"为什么这么验") | 下游: [07-技术细节与坑位手册](./07-技术细节与坑位手册.md) / [08-调参与容量手册](./08-调参与容量手册.md)
> 证据: `eval_reports/*.json|md`(四份报告) / `src/rag_v01/tests/test_evaluate.py`(24 项)

## 一、为什么要两段式(以及它白送了什么)

```text
第一段(数据面):  测试集 jsonl ──→ 逐题 [检索 + 最简生成] ──→ 中间产物 jsonl
                     (rag_v01.search + simple_answer)              │
                                                                   ▼
第二段(ragas 面):                        ragas.evaluate(四指标) ──→ 报告 json + md
```

三个好处, 第三个是意外收获:

1. **依赖隔离**: ragas 与主项目依赖互斥(见 §四), 但它**只吃 jsonl**。所以"检索 + 生成"这一半可以在主环境跑, ragas 那一半在独立环境跑 —— 两边的依赖不打架。
2. **可断点**: 检索+生成是最贵的一步(40 题要跑 40 次生成), 一旦落盘, 后面可以反复重评(`--samples` 仅评估入口)而不必重跑检索。
3. **天然支持跨系统对比**: 旧系统不需要 import 本包, 只要产出一份同格式 jsonl 就能和本系统同台评 —— 新旧双跑就是这么做的(旧系统那侧由一次性脚本产 jsonl, 用完即删)。

**边界的代价**: 报告里的"语料快照"(`doc_count` / `children`)是评估时从 Milvus 读的, 所以对**旧系统**那份报告来说它描述的是新内核的库, 不是旧系统真实用的 pgvector 库。读对比表时要知道这一点。

**第二段里"谁在打分"**: ragas 是**本地编排 + 远程判分** —— 框架在评估环境的 Python 进程里跑, 但它自己不含模型, 每一次打分都是对外请求:

- 入口是 `ragas.evaluate(...)`(`evaluation.py:311`, 函数 `ragas_evaluate` 起于 `:301`), 装配三样东西:
  - `metrics=build_metrics()`(`:237`): 四个指标类;
  - `llm=build_judge(cfg)`(`:219`): 经 `llm_factory` 装配的 **judge LLM**(`.env` 的 `RAG2_JUDGE_*`, 实际是 DeepSeek `deepseek-flash`, `temperature=0` / `max_tokens=2048`) —— context_precision / context_recall / faithfulness 三项的每一条判断都由它给出;
  - `embeddings=build_embeddings()`(`:248`): 百炼 `qwen3-vl-embedding` 适配器, 只服务 `answer_relevancy`(反推问题与原问题算余弦相似度)。
- 并发与容错在 `RunConfig(max_workers=4, timeout=120, max_retries=2, seed=42)`; 单题失败留 NaN(`raise_exceptions=False`)。
- 结果 `result.to_pandas()` → `summarize`(`:359`) 汇总成四指标均值 + 逐题明细 → 报告落盘。

一句话: **判分不在本地算, 在远程 LLM 与嵌入服务里算** —— 这也是"噪声带来自生成 + 判分两端"的根源(见 [05 篇](./05-质量检验策略与方法.md) §5.2)。

## 二、中间产物 jsonl 契约

每行一条样本, 字段与 ragas 对齐(`evaluation.py:36, 79-99`):

| 字段 | 来源 | 说明 |
|---|---|---|
| `question_id` | 测试集 | 归因时的定位键 |
| `user_input` | 测试集 `question` | ragas 的样本字段名 |
| `retrieved_contexts` | `[chunk.parent_text for chunk in hits]` | **保持 RRF 名次顺序, 不排序不去重** |
| `response` | `simple_answer(question, contexts)` | 最简生成器产出 |
| `reference` | 测试集 `ground_truth` | 参考答案 |
| `debug` | `debug_of(hits)` | 每题的两路名次明细; **ragas 不读**, 排障与归因用 |

三处刻意的设计:

- **`contexts` 取父块全文**而不是子块: 与最终喂模型的载荷同源, 也与 `kb_search` 的 `content` 口径同源, 于是"检索质量"与"模型看到的上下文"不会再各说各话。
- **不排序不去重**: 顺序本身就是信息(第一名在第几位), 重排会让 `context_precision` 的读数失真。
- **中间产物写进 `report_dir` 而不是 cwd**(`:568`): 评估命令会用 `--directory eval` 切换工作目录, 写 cwd 会落到 `eval/` 里去。

## 三、测试集契约

`TESTSET_FIELDS` 七字段(question_id / question / ground_truth / question_type / source_doc / reviewed / notes)。`load_testset`(`:101-116`)校验很严: 缺字段、`question` 或 `ground_truth` 为空 → 直接报错**并点出行号**。

为什么严: 这份测试集是"以后所有参数改动都要对着比"的参照物, 一条脏数据进来会安静地拉低读数, 比直接报错难查得多。

## 四、独立评估环境 `eval/`

### 4.1 为什么必须独立

`ragas >= 0.4` 经 instructor 要求 `rich<15`, 主项目钉的是 `rich>=15` —— **依赖互斥**。两条出路: 主项目放宽 rich, 或另建环境。选了后者, 主环境的 `pyproject.toml` 与 `uv.lock` **一个字节都没动**。

### 4.2 从零重建这个环境的清单

```bash
cd eval
uv add "langchain-community<0.4" "ragas>=0.4.3"            # 钉 langchain-community 的版本上限
# pyproject.toml 里加:
#   [tool.uv] override-dependencies = ["rich>=14,<15"]      ← 只在 eval 环境放宽 rich
#   [tool.uv.sources] taskforce = { path = "../" }          ← 路径依赖主包(editable)
uv sync
```

三条实测约束, 少一条就跑不起来:

| 约束 | 症状 | 原因 |
|---|---|---|
| `langchain-community<0.4` | `import ragas` 直接崩: `No module named 'langchain_community.chat_models.vertexai'` | 0.4 移除了该模块, 而 ragas 还在 import 它 |
| `override-dependencies = ["rich>=14,<15"]` | 装不上 / 主环境被连锁降级 | 环境级覆盖只作用于 eval, 放宽后 openai 会经 jiter 降到 <3.6(实测) |
| 路径依赖 `taskforce = { path = "../" }` | 找不到 `rag_v01` | 评估要真跑检索与 embedding, 需要主包的 `pymilvus` / `dashscope`(`rag2` extra) |

### 4.3 跑法(以及三个必踩的路径坑)

```bash
PYTHONPATH="<repo>/src" \
uv run --directory eval --env-file "<repo>/.env" \
  python -m rag_v01.cli evaluate \
  --testset "<repo>/data/eval_qa_v1.jsonl" \
  --report-dir "<repo>/eval_reports" \
  [--label rag_v01] [--limit 5] [--samples <既有中间产物>]
```

- `--env-file` 必须给**绝对路径**: `--directory eval` 会把 cwd 切到 `eval/`, 相对的 `.env` 找不到。
- `.env` **不会自动载入**: 只有 `settings/config.py` 读它, 裸 `python -c` 看不到 `RAG2_*`。
- 所有路径都给绝对路径(测试集、报告目录、中间产物), 否则会落在 `eval/` 里。
- `PYTHONPATH` 必须显式给 `<repo>/src`: `rag_v01` 靠 pythonpath 暴露(没进 hatch packages), 顺带把机器级的全局站点挤出 `sys.path`(实测会遮蔽 venv 里的包)。

跑之前确认两件事: ① Milvus 在跑且 500 篇语料已入库(否则检索回空、指标全崩; **入库用主环境跑** —— 评估环境的 torch 是 CUDA 版, 加载会崩); ② judge 会真扣费, 先 `--limit 5` 试跑看账单再放全量(见 §七)。

**依赖版本快照**(`eval/uv.lock`): ragas `0.4.3` / langchain-community `0.3.31` / instructor `1.17.0`。

## 五、ragas 接入的八个坑

`evaluation.py:188-216` 的 `_ragas_api()` 把 ragas 的公开面**集中在一个函数里**导入 —— 升级 ragas 时只改这一处 + `METRIC_ALIASES` 一处。八条实测坑:

| # | 坑 | 症状 | 对策 |
|---|---|---|---|
| 1 | 指标类名会变 | 报告列名变化 | `METRIC_ALIASES` 单一映射点(四指标口径名固定为 `context_precision` / `context_recall` / `faithfulness` / `answer_relevancy`) |
| 2 | 不要用已弃用的 `LangchainLLMWrapper` | 弃用警告 + 版本脆弱 | 用新接口 `llm_factory(model, client=openai.OpenAI(...), temperature=0, max_tokens=2048)` |
| 3 | judge 的 `max_tokens` 必须给足 | `IncompleteOutputException`: 结构化输出被截断 | `2048`: `answer_relevancy` 要模型生成 3 个反向问题, 默认预算不够 |
| 4 | 嵌入适配器要**八个别名** | `AttributeError: embed_query` | ragas 基类要求 `embed_text/embed_texts` + `aembed_text/aembed_texts`, 而内部**仍调旧名** `embed_query/embed_documents` —— 四个同步 + 四个 async 全给 |
| 5 | 基类强制 async | 想纯同步做不到 | 四个 async 方法只做 `to_thread`(全包唯一的 async 处, 不建事件循环) |
| 6 | `total_tokens` / `total_cost` 是**方法** | 直接塞进 json → bound method 序列化崩 | `_value_of` 统一按"可能是方法"处理, 且**容错**(没配 token 解析器时 `total_cost()` 会抛) |
| 7 | 单题失败会中断整跑 | 一题崩, 全场无结果 | `raise_exceptions=False`: 失败题留 NaN 继续跑 |
| 8 | 指标全 NaN 的题 | 均值失真 | `_mean` 忽略 NaN; **全 NaN 时返回 `None` 而不是 0**; 报告里单列 NaN 题目名单 |

第 4、6 两条最值得记: 它们都是"库的内部实现泄漏到调用方"的典型 —— 基类声明一套接口, 内部实现调另一套; 属性看起来像数据, 实际是方法。

## 六、报告结构

落盘两份, 文件名 `eval_<label>_<时间戳>.{json,md}`:

**meta 区**(可追溯的全部条件):
- 测试集路径 + `sha256[:16]` + 题数
- ragas 版本 / judge 型号 / 嵌入模型与模式
- 检索参数快照(`top_k` / `candidates` / `rrf_k` / `hnsw_ef`)
- contexts 口径(`parent_text`)与生成 prompt 版本(`v1`)
- 语料快照(`doc_count` / `children`)
- NaN 题目名单

**结论区**: 四指标均值表。
**明细区**(markdown): 逐题表格, 每题含 问题 / **参考答案** / **生成回答** / 上下文数 / 四个分数。生成回答那一列是排障金矿 —— 一看就知道是"没检索到"还是"检索到了没答对"。
**对比区**: 同目录下出现**异构 `system_label`** 的报告时, 自动追加一张并排对比表(`_compare_table`), 单测覆盖了这条。

## 七、耗时与费用

| 步骤 | 实测 |
|---|---|
| 500 篇语料入库 | **1m59s** |
| 40 题全量评估(检索 + 生成 + 四指标判分) | 约 **32 分钟**(基线那次; 旧系统对照那轮约 35 分钟) |
| 仅评估(固定既有中间产物) | 约 30 分钟(仍是 judge 在跑, 只有检索与生成省掉) |

生成与判分共用同一套 `RAG2_JUDGE_*` 配置(同一个 key 与限流池)。`--limit 5` 是**先试跑看账单**用的开关 —— 全量跑一次是真金白银, 改了 prompt 或指标先跑 5 题确认没崩再放全量。

费用统计目前**没接**: ragas 需要 token 用量解析器才能算钱, 本项目没配, 所以报告里成本字段是"不可用"。这条是已知缺口(见 [rag_0.1/TODO](../../../new_module/rag_0.1/TODO.md) 坑位 10.1), 不是 bug。

## 八、这套评估的已知盲区(引用结论时必须一起说)

1. **语料形态盲区**: 500 段语料一段一文件, 1 文档 = 1 父块 → 父子分块的"多子块 / 跨页 / 同父去重"**未被评估覆盖**。
2. **生成器差异**: 评估用的是最简生成器, 不是线上 answer 链路, 所以指标衡量的是"检索 + 简单生成"。
3. **噪声带**: 判分侧不可复现(faithfulness Δ0.20), 小差异不下结论(见 [05 篇](./05-质量检验策略与方法.md) §5.2)。
4. **参考答案是短语**: `context_recall` 偏乐观。
