## 2. 推进状态机(纯 Python)

```python
def _advance_plan(state, injected, tasks, thread_id) -> Command | None:
    """返回 None 表示无需短路,继续走既有路由;否则返回的 Command 直接结束本轮。"""
    plan = Plan.model_validate(state["plan"])

    # ① 对账:本轮回收的结果按 task_id 匹配 running 步
    if injected:
        for r in injected:
            plan.mark_by_task(r.task_id, r)      # failed→failed(级联),其余→done(冒烟修正)
        plan.cascade_skip()                      # 失败级联:依赖失败步的 pending→skipped

    # ② 解锁:ready 步分批派发(≤MAX_PARALLEL_SUBAGENTS=3,超出留待下轮)
    ready = plan.ready_steps()
    if ready and tasks is not None:
        jobs = [(s.assignee, _step_contract(plan, s)) for s in ready[:MAX_PARALLEL_SUBAGENTS]]
        for s, tid in zip(ready, tasks.submit(jobs, thread_id=thread_id)):
            s.task_id, s.status = tid, "running"
        # 派发复用 supervisor.py:117-121 同款 submit 调用形状

    # ③ 终态判定
    if plan.finished():                          # 无 pending 且无 running(含全 skipped)
        return Command(goto="answer", update={"plan": None, "messages": [
            AIMessage(f"计划执行完毕:\n{plan.snapshot()}")]})
        # answer 从 subagent_results 拿全部步结果汇总;messages[-1] 是 AUTO_NOTICE
        # ("请直接汇总结果",service.py:25),语义正好衔接
    if ready or injected:                        # 本轮有推进动作 → 短路结束,带快照
        return Command(goto=END, update={"plan": plan.model_dump(), "messages": [
            AIMessage(f"计划推进:\n{plan.snapshot()}")]})
    return None                                  # 有 running 在跑、本轮无新事件 → 不短路
```

返回 None 时**不短路**——继续走既有 LLM 路由(场景:有 running 步在后台跑,用户此刻插话,路由照常处理用户的新消息)。

## 3. 短路规则(何时跳过路由 LLM)

| 轮次类型 | 判定 | 行为 |
|---|---|---|
| **唤醒轮** | 最后一条消息 content 以 `PREFIX_SYSTEM_NOTICE` 开头(service.py:25,AUTO_NOTICE 前缀;REPL watcher 与 API /chat/summary 发的都是它) | 推进后**直接短路**:派发→END、收口→answer,不调路由 LLM |
| **用户轮** | 最后一条是真实用户消息 | 先推进(可能派发新批),再照常 LLM 路由处理用户新话;两者 update 合并 |
| **plan 活跃 + 用户新复杂问题** | 路由仍输出 `next="plan"` | 由 02 §2 的双保险兜住:plan_draft 发现 plan 已存在 → answer 提示,不覆盖 |

原理:确定性推进不需要 LLM 参与,短路省 token 且杜绝路由 LLM 干扰调度;唤醒轮的消息(AUTO_NOTICE)本来就无用户语义,路由它纯属浪费。

## 4. task_id 对账(零契约变更的机制)

1. `tasks.submit()` 返回 task_ids,与 jobs 顺序严格对应(tasks.py:36-49);
2. plan_confirm / 推进块把 task_id 回填 `PlanStep.task_id` 并标 running;
3. 后台 `_run` 产出的 ResultSummary 带 task_id(summary.py:22;**实施 M1 时验证正常路径该字段确实被子图回填**,若为空则在 tasks.py `_run` 尾部统一 `model_copy(update={"task_id": task_id})` 打标,一行);
4. 下一轮 drain_done(tasks.py:51-64,消费即清)返回结果,推进块按 task_id 匹配。

## 5. REPL 进度快照(零新机制)

快照文本由 `Plan.snapshot()` 渲染,嵌在派发确认/推进/收口的 AIMessage content 里,REPL 与 API 前端零改动可见:

```
📋 计划:对比宁德时代与比亚迪 2024 年毛利率
  ☑ s1 查两司年报毛利率 —— 毛利率已获取(research)
  ▶ s2 计算差值与趋势(executor)
  ☐ s3 ...
  ✗ s4 ...(failed,原因摘要)
  ⊘ s5 ...(依赖 s4 失败,已跳过)
```

符号:☐ pending / ▶ running / ☑ done / ✗ failed / ⊘ skipped。

可选增强(本期不做,TODO 遗留项):run_turn 的 updates 流已遍历节点 update(service.py:57-66),可加 `on_plan` 回调实时渲染,前端可做独立 plan 帧。

## 6. 预算与边界

- **recursion_limit**:plan_draft(1) + plan_confirm(1) + 每步(推进轮+唤醒轮)×5(10) + 收口(1)= **13 轮**,低于默认 25(模块 10 已放宽至 40,见 ROADMAP M10 备注),充裕。用户中途多次插话会 +1/轮,GraphRecursionError 兜底已有(service.py:67-72),不改 limit,先观测。
- **并行写冲突**:两个无依赖 executor 步写沙箱同一文件互踩——靠 planner 提示词用 depends_on 表达隐性依赖规避(02 §4),不做代码级互斥。
- **双派发源**:推进块先于路由执行,唤醒轮短路后路由不跑,不存在同轮双派发;用户轮推进+路由并存时,路由的 dispatch 是用户新话触发的独立任务,与 plan 并行无冲突(TaskManager 按 thread 累加 pending,on_done 全批完成才触发,tasks.py:113-117)。
