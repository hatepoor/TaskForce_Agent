# plan_0.1 · 02-规划与确认节点

> 两个新主图节点:plan_draft(LLM 生成计划)与 plan_confirm(HITL 确认 + 首批派发)。
> 实现落 `src/agent/planner.py`,由 `build.py` 挂载。

## 1. 为什么拆成两个节点

`interrupt()` 的语义:节点内调用即挂起;resume 后**整个节点重跑**,interrupt 处直接返回 resume 值。若把"调 LLM 生成计划"和"interrupt 确认"放同一节点,resume 重跑会**再调一次 LLM**(温度 0.7,计划可能变化)——副作用不可重入。

拆开后:`plan_draft` 只跑一次(LLM),`plan_confirm` 是纯确定性节点(读 state.plan → interrupt → 分支),重跑零副作用。ask 节点已是同款约束(ask.py:20-26,ADR-0008)。

## 2. plan_draft_node(新)

```python
def plan_draft_node(state, llm) -> Command:
    goal = 最后一条用户消息内容
    try:
        draft = llm.with_structured_output(PlanDraft, method="function_calling").invoke(
            [SystemMessage(load_prompt("planner")), HumanMessage(goal)]
        )
        draft.validate_structure()
    except Exception as e:                                   # 兜底与 route_node 同风格
        return Command(goto="answer", update={"messages": [AIMessage(
            f"任务规划失败({e}),请直接描述需求,我来逐步处理。")]})
    return Command(goto="plan_confirm", update={"plan": draft.to_plan().model_dump()})
```

要点:

- **method 必须显式 `"function_calling"`**——supervisor.py:94-97 已踩:langchain-openai 1.x 默认 json_schema,DeepSeek 端点 400 后静默兜底。
- 失败兜底 goto answer(与 route_node 解析失败回退一致,supervisor.py:98-100),不做"退化为单任务派发"(复杂问题单任务派发正是要避免的)。
- 双保险:本节点开头检查 `state.get("plan")` 非 None(已有计划进行中)→ 不生成新计划,直接 goto answer 提示"已有计划执行中"(防旧 plan 的 task_id 对账被覆盖丢失,running 步成孤儿)。
- 本节点不写 messages(计划还不是对话内容,快照在 plan_confirm 的确认消息里);不需要注入 tasks(本节点不派发)。

## 3. plan_confirm_node(新,HITL)

### 3.1 interrupt 载荷

`contracts/interrupt_payload.py` 新增 `plan_payload(plan_text)` → `{"kind": "plan", "text": plan_text}`,与 ask_payload 同构(c5)。三处联动,漏一处就 ImportError 或识别不到:

- `InterruptKind` 与 `InterruptPayload.kind` 的 Literal 都要加 `"plan"`;
- `classify_interrupt` 的 kind 判定放宽为 `("ask", "memory", "plan")`;
- **`contracts/__init__.py` 同步导出 `plan_payload`**(节点从包顶层 import;2026-09-24 实测漏此项会 `ImportError: cannot import name 'plan_payload'`)。

### 3.2 resume 协议

| 用户输入 | 语义 |
|---|---|
| `y` / `yes` / `确认` | 批准 → 派发首批 |
| 其他任意输入 | 取消 → 清 plan,goto answer(消息里回显输入,提示可换种问法) |

宽松匹配取消侧:计划有误时任何具体修改意见本期都不生效,宁可让用户取消重问,不猜测意图。

### 3.3 节点逻辑

```python
def plan_confirm_node(state, tasks, config) -> Command:
    plan = Plan.model_validate(state["plan"])
    decision = interrupt(plan_payload(plan.snapshot()))
    if not _approved(decision):
        return Command(goto="answer", update={
            "plan": None,
            "messages": [AIMessage("已取消执行该计划。")],
        })
    # 批准:装配首批(无依赖步),走 TaskManager 异步派发(方案 A)
    thread_id = (config.get("configurable") or {}).get("thread_id") or ""
    ready = plan.ready_steps()                       # 首批:depends_on 为空的步
    jobs = [(s.assignee, _step_contract(plan, s)) for s in ready[:MAX_PARALLEL_SUBAGENTS]]
    ids = tasks.submit(jobs, thread_id=thread_id)
    for s, tid in zip(ready, ids):                   # 回填 task_id + 标 running
        s.task_id, s.status = tid, "running"
    return Command(goto=END, update={
        "plan": plan.model_dump(),
        "messages": [AIMessage(f"计划已确认,已派发首批 {len(ids)} 步:\n{plan.snapshot()}")],
    })
```

要点:

- `_step_contract(plan, step)` 装配 TaskContract:task=step.detail、user_utterance=plan.goal、input_data={}(step 关联靠 task_id 回填,不塞 input_data)、output_schema_hint 同 build_contract(supervisor.py:34)。
- **首批派发与 supervisor.py:117-121 的异步 dispatch 完全同款**(jobs → submit → 确认消息 → END)。
- 派发上限:首批 ready 可能超过 MAX_PARALLEL_SUBAGENTS=3,截断,余下步留待后续轮解锁(supervisor 推进块负责,见 03)。
- `tasks is None`(单测无管理器):本节点不支持同步 Send 备胎,直接 goto answer 附说明(取舍记录在 ADR-0012)。

## 4. planner.md 提示词规范(新增 `src/prompts/planner.md`)

硬约束(全部写进提示词,与 validate_structure 双保险):

1. 步数 1~5。
2. 每步 detail **自包含**:目标+输入+输出要求+成功标准;依赖前序步时写明"需要前序步产出什么"(子图只看契约四件套)。
3. assignee 三选一:检索知识库→retriever;联网查最新信息→research;计算/数据处理/图表→executor。
4. depends_on 只能引用 id 更小的步;无依赖就不填。
5. 防过度拆分:一次能查清的不拆;两步能合成一步的不拆。
6. 最终汇总建议不进计划——收口由主图 answer 承担(见 03 §2),计划只含"产生事实与数据"的步。

投资调研正反例(写进提示词):

- ✅ 拆:「对比宁德时代与比亚迪 2024 年毛利率并给建议」→ s1 research 查两司年报毛利率 → s2 executor 计算差值与趋势(s1→s2 依赖)。
- ❌ 不拆:「宁德时代 2024 年毛利率是多少」→ 单跳检索,supervisor 直接 dispatch retriever。

## 5. build.py 挂载

```python
b.add_node("plan_draft", lambda s: plan_draft_node(s, llm))
b.add_node("plan_confirm", lambda s, config: plan_confirm_node(s, tasks, config=config))
b.add_edge("plan_draft", "plan_confirm")
```

supervisor → plan_draft 由 route_node 的 `Command(goto="plan_draft")` 动态跳转,不加静态边。节点总数 7→9;messages 流白名单(service.py:52 `{"answer","ask"}`)**不含**这两个节点——它们的 structured output 与确认文本不进打字机流,符合既有过滤语义,无需改动。
