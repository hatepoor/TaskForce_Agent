### 4.7 坑位汇总

| 坑 | 说明与对策 |
|---|---|
| 首次运行下载模型 | 布局模型 + TableFormer 数百 MB, 从 HuggingFace 拉; 离线/直连不畅会"假死"在首次 `convert()`。对策: 设 `HF_ENDPOINT=https://hf-mirror.com`(用于 docling 解析模型下载, 见 [01.1-目标与决策](./01.1-目标与决策.md) §2.5), ingest 前先用 1 页 pdf 暖缓存; Windows 杀软扫描大文件会让首跑更慢 |
| 大文件耗时与内存 | 布局模型逐页 CPU 推理: 百页 pdf 分钟级耗时、内存 GB 级峰值; `images_scale` 越高图片驻留越多。对策: ingest 逐文件串行 + 每文件打进度日志(不要在外层再套并发——docling 内部已多线程, 外层并发会让内存翻倍); 超大 pdf 先单独试跑看内存; 极端情况按 `page_range` 分段转换, 但**分段后 `page_no` 需重映射**(docling 内部 `DoclingDocument.concatenate` 有先例, 不建议首版做) |
| 中文扫描 PDF 的 OCR 质量 | `RAG2_DO_OCR` 开了也只是"能出字": 默认引擎对中文一般, tesseract 路线要 `chi_sim` 语言包, 表格经 OCR 基本损毁。对策: 扫描件先抽 5~10 页人工看识别质量, 烂的不入语料或降级为"仅标题"; 引擎候选(EasyOCR / Tesseract / RapidOCR)类名与效果【待验证】, 注意 `force_full_page_ocr` 已废弃, 现行为 `ocr_options.mode = OcrMode.FULL_PAGE` |
| OCR 结果破坏结构假设 | 扫描件的表格/标题都是 OCR 猜的, `heading_path` 与表格行列不可信 → 该文档在 `IngestReport` 里单独标注"开了 OCR, 检索质量另看" |
| docling 版本漂移 | 本篇标【待验证】的 API 按各自验证命令跑一遍再定稿; 版本以 [./01-环境与依赖.md](README.md) 锁定为准 |
| Windows 路径与编码 | 全链路用 `pathlib.Path` 传路径不在字符串上拼; 落盘图片用二进制模式; 库模块不许动全局 stdout(GBK 坑的 reconfigure 只放 cli.py, 见 [07.3-实现要点](./07.3-实现要点.md) §4.2) |
| 目录名/包名 | 目录原名 `rag_0.1`(点号是包分隔符, 不能当包名)已于 2026-09-20 改名为 **`rag_v01`**: 包内一律相对导入(`from . import images` / `from ..contracts import ...`), 包外(测试与调用方)用 `from rag_v01.parsers import ...`。2026-09-22 起与其它六个包**同深度**地登记进 `hatch packages`(源码目录 `src/rag_v01/`), 靠 editable 安装暴露(原先的 `pythonpath = ["src/new_module"]` 已随之删除); 移植见 [./07-接口设计与移植方案.md](README.md) §4.6 |
