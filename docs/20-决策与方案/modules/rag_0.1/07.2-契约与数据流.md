## 三、数据流与接口契约

### 3.1 facade 三入口

| 入口 | 签名 | 产出契约 | 上游分篇 |
|---|---|---|---|
| `ingest` | `ingest(paths: list[str \| Path]) -> IngestReport` | `IngestReport` | 编排 [02](README.md)→[03](README.md)→[04](README.md) |
| `search` | `search(query: str, top_k: int \| None = None) -> list[RetrievedChunk]` | `list[RetrievedChunk]` | [05](README.md) |
| `evaluate` | `evaluate(testset_path: str \| None = None, report_dir: str = "./eval_reports", *, samples_path=None, system_label="rag_v01", limit=None) -> EvalReport` | `EvalReport` | [06](README.md)(**需评估环境** `eval/`, 见 [06.1-目标与决策](./06.1-目标与决策.md) §2.7) |

数据流总览(与 [00-总览](README.md) 一致):`ingest` = parse→clean→chunk→embed→store;`search` = 双路 top-20→手写 RRF(k=60)→top-5 子块→按 parent_id 回溯 parents 取父块并按父去重;`evaluate` = 检索 + 最简回答生成 + ragas 四指标。

**内存纪律(硬约束, 写 `ingest.py` 时不许破)**:`ParsedDoc` 只在内存里传递([02.2-契约与数据流](./02.2-契约与数据流.md) 不落盘, 见其 §三 接缝约定), 所以**必须逐文件处理**——`for path in paths: parse → clean → chunk → embed → upsert → 丢弃`, 峰值内存 = 最大单文件的解析产物 + 该文件的子块向量, 与语料总量无关。禁止"先把所有文件 parse 完再统一入库"(那是把整语料的 items + 向量攒在内存里, 语料一多就炸)。要留意的三处放大: ① 向量是 Python `list[float]`, 1024 维一组实测约 32 KB(list 槽 8 KB + float 对象 24 KB), 单文件级没问题、跨文件批处理才会失控(真要批处理就换 `array('f')`/numpy float32, 省 8 倍); ② 图片 base64 只在 [04.3-实现要点](./04.3-实现要点.md) 每请求 ≤5 张的窗口里瞬时存在, 且 [02.3-实现要点](./02.3-实现要点.md) 已把图片字节外置到磁盘只留路径; ③ 长期驻留进程(如 API 里跑 ingest)不许把结果塞进模块级全局——模块级只放 `lru_cache` 的 client/embedder 单例, 不放数据(§4.4)。

### 3.2 contracts.py 契约示例(节选,以落地为准)

```python
# 本篇只列 ingest() 与 facade 的报告契约; 其余四个契约的形状以各自分篇为唯一出处(见下方注)。
@dataclass
class IngestReport:
    ok_sources: list[str]            # 成功入库的文件名
    failed: dict[str, str]           # 文件名 -> 失败原因(解析失败/入库失败)
    total_parents: int
    total_children: int
    warnings: dict[str, list[str]]   # 文件名 -> 警告(解析 warnings / 清洗统计 / 超长前置检查等,模块 02/04)

@dataclass
class EvalReport:
    metrics: dict[str, float]        # context_precision/context_recall/faithfulness/answer_relevancy
    question_count: int
    report_dir: str                  # json+markdown 基线报告落盘位置
```

`ParsedDoc`([02.2-契约与数据流](./02.2-契约与数据流.md))、`ParentChunk` / `ChildChunk`([03.2-契约与实现](./03.2-契约与实现.md) §3.1 九字段表)、`RetrievedChunk` / `ChildHit`([05.2-契约与数据流](./05.2-契约与数据流.md) §3.2,父块上下文 + 命中子块明细)的字段以各自分篇为唯一出处,此处不重复定义。

### 3.3 元信息九字段(定稿,逐字)

`chunk_id, parent_id, doc_id, source, page_no, heading_path, chunk_type(text|table|image), char_len, created_at`——父块同样携带(其 `parent_id` 为空)。命名固定,不得增删改名;Milvus 侧落地为 children 的标量字段 + metadata(JSON),见 [04](README.md)。
