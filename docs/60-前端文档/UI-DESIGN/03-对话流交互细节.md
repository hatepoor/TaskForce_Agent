## 3. 对话流交互细节(重点)

### 3.1 轮次结构

一个"轮次"(Turn)从用户发送开始,到流结束为止。**挂起不结束轮次**——用户回答后同一轮次继续追加内容。轮次内从上到下固定顺序:

```
用户消息 → 路由轨迹条 → 子任务批次卡 → AI 正文 → 用量角标
```

轮次之间用 24px 空白分隔,**不画分隔线**。每个轮次是独立的数据对象,流式增量只影响最后一个未闭合轮次。

### 3.2 消息气泡类型

**用户消息**——右对齐,`--bg-raised` 底,6px 圆角,max-width 80%,`white-space: pre-wrap`。不加头像,不加"你"标签。

**AI 回复**——左对齐,**不用气泡**,直接铺在背景上(气泡会限制 markdown 排版)。限宽 760px。流式追加时末字符位置一个 1px 宽闪烁竖条光标;**流式期间渲染纯文本**(`pre-wrap`),结束后才走 Markdown(半截语法渲染不出正确结果,顺便省性能,见 ARCHITECTURE 坑 5)。结束后光标消失,正文下方 12px 处出现元信息行:`2 次调用 · 入 3.2k / 出 412 tok`。

> **2026-09-18 补(用户要求)**:AI 正文左侧加 26px 中性图标头像(`AiAvatar.vue`,三点连线语义),与正文顶端对齐;头像本身不抢强调色,仅在"思考中"时描边转为 `--accent` 并轻微呼吸。

**路由轨迹条**——本轮所有 `route` 事件**聚合成一条**,默认一行摘要,可点开:

```
收起态:
  ● 派发 · retriever + research  2 项并行 ▸

展开态:
  ▾ 路由轨迹 (3 步)
    ① 派发 2 项
       ● retriever  检索本地知识库中 pgvector 的部署方式
         理由:问题涉及本地文档
       ● research   联网查 FAISS 的运维成本与社区活跃度
         理由:需要最新外部信息
    ② 汇总作答
```

`next` 到中文映射:`answer→汇总作答`、`ask→需要补充信息`、`memory→记忆写入`、`dispatch→派发 N 项`。流进行中圆点轻微呼吸(2s 周期透明度 1→0.4),流结束变实心静止。**这是整个界面唯一的动画。**(2026-09-18 补:随 AI 头像一并加入"思考中三点跳动 + 头像呼吸",见 §3.2 AI 回复注;动效仍限于这三种状态指示,无装饰性动画。)

**子任务批次卡**——一次 `dispatch` 生成一张卡:

```
进行中:
  ┌─────────────────────────────────────────────────────┐
  │ 派发 2 个子任务                                       │
  │ ● retriever  检索本地知识库中 pgvector 的部署方式      │
  │ ● research   联网查 FAISS 的运维成本与社区活跃度       │
  └─────────────────────────────────────────────────────┘
```

**注意(异步派发架构的硬约束,2026-09-18 更新)**:后端是"异步派发"——supervisor 提交任务立即返回"已派发"确认并结束本轮,子任务结果在**下一轮** `drain_done()` 时才回灌。因此 SSE 流内等不到"已完成"信号;原计划靠批次卡示意,现改为**前端轮询 + 自动汇总**(`useTaskWatch` 3s 探 `GET /chat/tasks`,全批完成自动发起 `POST /chat/summary`):派发确认与汇总正文都直接落在对话流里,**不再有批次卡**。语义与 REPL 一致(用户轮优先,流式期间不抢跑)。

**用量角标**——AI 正文下方 12px 灰字,**不做卡片、进度条、颜色**。由于 `usage` 事件是进程累计值,前端做差显示本轮值;右侧抽屉 UsagePanel 展示进程累计值,标签写清("本轮" / "进程累计")。

### 3.3 interrupt 挂起卡

判别规则(B3 信封):按 `interrupt.kind` 分派——`ask` → 问询卡,`memory` → 确认卡,`unknown` → 禁用输入 + "检测到未知类型的挂起" + 新开会话出口。挂起期间 `Composer` 置灰禁用,提示"请先回答上方问题"。

**ask 问询卡**:

```
  ┃ 需要补充信息
  ┃ ┌───────────────────────────────────────────────────────┐
  ┃ │ 请问要检索的知识库范围是?你希望覆盖哪几份文档?          │
  ┃ │                                                       │
  ┃ │ ┌───────────────────────────────────────────────────┐ │
  ┃ │ │ 输入你的回答…                                      │ │
  ┃ │ └───────────────────────────────────────────────────┘ │
  ┃ │ Enter 发送 · Shift+Enter 换行                          │
  ┃ └───────────────────────────────────────────────────────┘
  ┃  2px 左边框,用 --accent
```

- 卡片出现时**输入框自动聚焦**并强制滚入视野(`scrollIntoView({block:'nearest'})`,即使用户正在上滚)。
- 发送 → `POST /chat/answer`,卡片**立即原地折叠**为已解决态,新流追加到同一轮次。
- 返回 400(挂起已在别处恢复):卡片标失效,提示"该挂起已失效",触发会话状态刷新。

**memory 确认卡**:

```
  ┃ 记忆写入确认
  ┃ ┌───────────────────────────────────────────────────────┐
  ┃ │ 将写入长期记忆(仅存于你本地的 pgvector):              │
  ┃ │ ┌───────────────────────────────────────────────────┐ │
  ┃ │ │ 用户偏好用 uv 管理 Python 依赖,不用 pip。          │ │  ← proposal 原文
  ┃ │ └───────────────────────────────────────────────────┘ │
  ┃ │ 来源:本轮对话自动提案        [ 忽略 ]  [ 记入记忆 ]    │  ← 主按钮 accent
  ┃ └───────────────────────────────────────────────────────┘
```

- 提案文本引用块样式(左 2px 竖线 + `--bg-input` 底)。
- 主按钮 accent;次按钮 ghost;**默认焦点在"忽略"**,回车不误触写入。
- 两按钮都走 `POST /chat/confirm`(true/false),返回 SSE。
- **已解决态**(两种卡共用),折叠为一行,保留在历史里:

```
  ✓ 已补充回答 · "只看 docs/ 下那几份"                    14:22
  ⊘ 未记入长期记忆                                         14:22
```

### 3.4 空态 / 加载态 / 错误态

**空态**(无会话或新会话首屏):居中 520px 宽区域,一行标题 + 一行说明 + 三个示例问句按钮(点击**填入** Composer,不直接发送):

```
                        本地 Agent 工作台

     可以问我:本地知识库里的文档、需要联网查的最新资料、需要跑起来验证的代码。

     ┌────────────────────────────────────────────────────┐
     │ 总结一下 docs/ 里关于记忆设计的那部分                │  ← 点击填入输入框
     │  知识库检索                                        │
     ├────────────────────────────────────────────────────┤
     │ 查一下 pgvector 0.7 的 HNSW 参数默认值,给出建议      │
     │  联网调研 + 知识库检索                              │
     ├────────────────────────────────────────────────────┤
     │ 写段脚本统计 docs/ 下每个 md 的字数                  │
     │  沙箱执行                                          │
     └────────────────────────────────────────────────────┘
```

**加载态**:用户发送后**立刻**插入用户气泡与一条空的 AI 正文占位(只有一个闪烁光标),**不做骨架屏**。若 800ms 内无任何事件到达,光标上方补一行 12px 灰字"正在路由…";**首轮冷启动**(惰性装配图 + MCP 可能几十秒)1s 内给"正在初始化智能体…"反馈,防止用户重复点击。

**错误态**:分三类,处理方式不同。

| 情形 | 表现 | 可做的操作 |
|---|---|---|
| 请求未发出/HTTP 非 2xx | 错误条:`连接失败:502 · 服务是否在运行?` | 重试(重发同一请求) |
| 流中途断开(已有部分 token) | 正文保留,下方接错误条:`连接中断,以上内容可能不完整` | 复制已生成内容 / 重试 |
| B4 后 `error` 帧 `code: "recursion_limit"` | 正常正文样式:`本轮任务循环过深,已中止。请把需求拆小一点再试。` | 无(它就是一条正常回复) |

```
  ┌──────────────────────────────────────────────────────┐
  │ !  连接中断,以上内容可能不完整                          │
  │    [ 重试 ]  [ 复制已生成内容 ]                         │  ← 边框 --danger,底色透明
  └──────────────────────────────────────────────────────┘
```

**关于"重新生成"——明确不做。** 后端挂 checkpointer,重发同样文本会产生第二条重复用户消息污染上下文;真正的重新生成需要"回退 checkpoint 重跑"接口,当前不存在。首版只提供**重试**(仅限请求失败或零输出情形),流中断时提供**复制**让用户自己重发。宁可少一个按钮,不做一个语义错误的按钮。

### 3.5 流式与滚动

fetch + `response.body.getReader()` 手工解析(POST 不能用 EventSource)。解析器按 `\n\n` 切帧(先归一化 CRLF),`data: ` 前缀后 `JSON.parse`,单键分发。**token 追加用 16ms rAF 节流批量写入**(非响应式缓冲拼接后一次性赋值,见 ARCHITECTURE 坑 5)。
