# agent_opt_0.1 · 00-优化报告

> 状态:**报告定稿,实施方案待拆**(2026-09-28)。本篇只做诊断与优化项清单;确认范围后按 rag_0.1 先例拆 01/02/03 方案文档 + TODO.md,再动代码。
> 结论先行:效果差的主因是**子图回传双重截断**;麻烦的主因是**路由 LLM 负担过重 + 异步派发固定开销**。推荐 P0(成稿回传)→ P1(retriever 并入)→ P2(路由短路)三步,P3(模型分档)观望。

## 一、背景

用户体感:当前 agent 框架"过于麻烦的同时,效果还不好"。本报告通读核心链路代码(supervisor / answer / ReAct 骨架 / retriever / research / ResultSummary 契约 / supervisor.md)后给出实证诊断与优化项,全部结论带代码出处,不凭印象。

## 二、现状链路速览

```
用户消息 → supervisor(路由 LLM,5 动作 × 12 规则)
  ├─ answer:记忆/时钟工具循环 → 生成回答
  ├─ dispatch:TaskManager 后台派发 3 子图(retriever/research/executor)
  │    └─ 完成 → 唤醒轮(supervisor 再过一次路由 LLM)→ answer 汇总
  └─ plan:planner → 用户确认 → 分批派发 → _advance_plan 确定性推进
```

子图与主图之间唯一的结构化通道是 `ResultSummary`(结论/要点/data/sources);answer 汇总时经 `_render_results(with_evidence=True)` 把依据渲染进消息流。

## 三、实证诊断

### 诊断 1|子图回传"双重截断"——效果上限的第一实锤

子结果从子图到汇总模型要过**两道截断**,每一道都在丢正文:

| 环节 | 位置 | 限制 |
|---|---|---|
| 子图 data 收集 | `subagents/research.py:16,56,57` | results ≤8 条、fetches ≤5 条 × 每条节选 2000 字 |
| answer 依据渲染 | `answer.py:30-33` + `_render_evidence` | hits 每条 `_brief(250)` 字、fetches 节选 600 字、**单结果依据块硬闸门 1200 字**、来源 ≤5 |

实测含义:research 抓 3 篇网页 × 2000 字进 data,汇总模型实际只看到合计 ≤1200 字;KB 问答更紧——hits 4 条 × 250 字 ≈ 1000 字。**汇总质量的上限就是让模型看这一千字。**

而子图内部模型其实见过完整正文(`react.py` 私有消息预算 16k 字符),信息是在**回传边界**上丢的。历史事故同源:`research` 汇总"只回收了开头片段"(prose/JSON 协议坑,见 troubleshooting/plan_0.1.md)、fetches 收不到后补 `_collectFetches`——都是这条窄管道的症状。

### 诊断 2|路由 LLM 负担过重——麻烦与不稳的主因

- `prompts/supervisor.md` 要求路由 LLM 同时持有:5 种动作 × 12 条硬性规则 × 3 子智能体能力清单 × 记忆规则。规则越叠越多,路由错一次全链路白跑。
- 其中两条规则**纯确定性**,现在却每次都烧一次路由 LLM:
  - 规则 5(有已回收结果必须 answer):每个非 plan 的汇总轮都要过一遍路由 LLM(plan 场景已有唤醒轮短路,普通派发没有);
  - 规则 12(用户消息带 URL 必须 research)。
- 结构化路由已有两次事故记录:json_schema 400(需显式 `method="function_calling"`)、思考模式 × 强制 tool_choice 400(逼出 routeLlm 双实例)。

### 诊断 3|retriever 子图的隔离收益倒挂

`subagents/retriever.py`:MAX_ITERATIONS=5 的 ReAct 循环(实际提示词限"最多 2 次检索"),单工具(kb_search)。它把 KB 检索隔离在 16k 私有上下文里,代价是回传只能走诊断 1 的窄管道——**隔离带来的质量收益被回传损耗吃掉**。answer 侧已有现成工具循环(`_answer_with_memory`,MEMORY_LOOP_MAX=4),kb_search 挂进去即可直达原文,摘要环节整体消失。
> (2026-09-28 后记:诊断成立,但"并入 answer"的解法被用户否决,retriever 保持独立子智能体;回传损耗改由 P0 的 report 协议在 retriever 收尾处覆盖——隔离保留,损耗消掉。)

### 诊断 4|单模型撑全部角色

`build.py:make_llm`:路由/规划/双子图/汇总全用同一模型,routeLlm 仅 thinking=disabled 之差。多角色架构的"分工红利"(快模型做裁决、强模型做生成)完全没有兑现。

## 四、优化项清单

| 编号 | 项 | 核心改动 | 涉及面 | 收益 | 规模 |
|---|---|---|---|---|---|
| **P0** | 成稿回传 | `ResultSummary` 加 `report: str = ""`(无长度上限);子图 JSON 收尾协议加 report 字段(模型在收尾消息里直接写完整 markdown 成稿);`extract_answer` 提取;answer 优先注入 report 原文,无 report 退回现有 evidence 渲染 | `contracts/summary.py`、`subagents/react.py`、`research.py`、`executor.py`、`retriever.py` 收尾、3 个子图提示词、`answer.py` | 汇总基于完整成稿,双重截断失效;**零额外 LLM 调用**(搭现有收尾消息);旧 checkpoint 兼容(缺省空串) | 小 |
| **P1** | retriever 并入 answer | `kb_search` 进 `ANSWER_TOOLS`;删 retriever 子图与提示词;`Route.tasks[].agent`/`Task` 枚举收窄为 `research\|executor`;BUILDERS 注册表、build_graph 直挂节点、plan 派发面同步收窄 | `answer.py`、`contracts/route.py`、`build.py`、`tasks.py`、`supervisor.md`、`answer.md`、planner 提示词、tests(test_retriever 移交 answer 侧) | 删一整个子图的胶水;KB 问答原文直达;派发/plan 少一类分支 | 中 |

## 五、不动项(有意为之的设计,勿"修复")

- **plan 确定性推进**(`_advance_plan`):代码重但它是简历核心卖点且已稳(ADR-0012);
- **全同步约束**(ADR-0009):改动会震动 CLI/API/Studio 三入口;
- **interrupt 单挂起点**(ADR-0008/0012):动它等于重画状态机;
- **TaskManager 台账机制**:P1 只减类型不改机制;`react_msgs` 私有键等红线照旧。

## 六、实施顺序与验收

1. **P0 单独落地**即可验证效果:全量 pytest 绿;新增测试(extract_answer 提取 report / answer 优先消费 report / 无 report 回退 evidence);冒烟同一道 URL 调研题,汇总应引用明显更多正文细节。
2. P1 落地:全量 pytest 绿;路由枚举无 retriever;KB 问答冒烟中 answer 直接引用命中原文(不再有"检索子智能体返回了什么"的中间层)。
3. P2 落地:汇总轮与 URL 轮不再出现路由 LLM 调用(轨迹/日志验证),简单问答延迟可感下降。
4. P3 等 P0~P2 稳定后评估是否值得做。

教学模式分工不变:契约与业务代码我给完整清单、你亲手誊写;`tests/` 与文档我负责。
