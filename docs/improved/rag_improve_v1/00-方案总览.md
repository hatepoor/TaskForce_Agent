# 模块 00 · 方案总览(共享设计)

> 本文件是全优化共享的定稿设计:架构、检索流程、契约、坑表、文件清单。分模块推进时只读对应模块文档,细节有出入以本文件为准。

## 1. 目标与范围

- **做什么**:新增 Python 侧内存 BM25 索引(rank_bm25 + jieba 分词),检索时与现有向量路并行召回,RRF 公式融合排序;存量数据零迁移(首次检索懒重建即覆盖)。
- **不做什么**:不引入外部检索服务(ES/Qdrant);不换 PostgreSQL 镜像(ParadeDB);不改 PG 表结构(方案 B 的 tsvector 列为备选,本次不做);不引入 async;不改 `kb_search` 工具接口与 `RAGStore.search` 签名。
- **效果目标**:专名/精确词命中率提升(补向量路硬伤);Recall@5 / MRR@5 ≥ 纯向量基线。

## 2. 前置依赖与现状核对

| 依赖 | 需要其中的什么 |
|---|---|
| 模块 04(RAG 内核,已完成) | `RAGStore`(documents/chunks 双表)、`embed_texts`、`split_text` |

## 3. 升级后架构与检索流程

### 3.1 架构(新增组件)

```
                    ┌─────────────────────────────────────────────┐
                    │  tools/rag/bm25.py(新增)                    │
                    │  ├─ tokenize():jieba.cut_for_search+过滤    │
                    │  ├─ Bm25Index:内存 BM25(懒加载+脏标记+锁)    │
                    │  └─ rrf_fuse():RRF 融合排序                  │
                    └──────────────┬──────────────────────────────┘
                                   │ 注入 / 调用
  消费方(kb_search / cli / repl / api)
        │  search(query, top_k)  [签名不变]
        ▼
   RAGStore.search ──┬── 向量路:embed_texts → SQL `<=>`(原逻辑,抽 _search_vector)
                     └── 关键词路:tokenize → Bm25Index.search
                          ↓
                     rrf_fuse(双路候选,  k=60, M=5) → 原 dict 形状返回
```

- **数据流(检索)**:query → 双路并行取候选(各 top_M=5)→ RRF 融合 → 取 top_k=5 → 原形状返回;score 语义翻转(**越大越相关**)。
- **数据流(写入)**:`upload`/`delete` 成功后调用 `Bm25Index.mark_dirty()`;下次检索懒重建,不即时更新。
- **依赖方向**:`tools/rag` → `settings`(不变);`bm25.py` 零依赖(纯函数层,不连库)。

### 3.2 升级后 RAG 检索流程(完整时序)

```
用户/子智能体 → kb_search(query, top_k=5)   [ReAct retriever 子图,工具接口冻结]
  └→ RAGStore.search(query, top_k=5)
       ① 向量路:_search_vector(query, top_M=5)
          embed_texts([query]) → SQL: ORDER BY embedding <=> qvec LIMIT 5
          → 候选 A:[{chunk_id, doc_id, seq, score_cos(越小越近)}]
       ② 关键词路:tokenize(query) → Bm25Index.search(query, top_M=5)
          若索引未构建/已脏 → 锁内重建(读 chunks 全量 content → BM25Okapi)
          → 候选 B:[{chunk_id, score_bm25(越大越相关)}]
       ③ 融合:rrf_fuse(A, B, k=60)
          score = Σ 1/(k + rank),两路候选按各自排名并集,取总分 top_k
       ④ 回填原字段(doc_id/filename/seq/content/score),score 为 RRF 融合值
  └→ 返回原 dict 形状列表(kb_search 组装 JSON,SNIPPET_LIMIT 截断不变)
```

### 3.3 score 语义翻转(契约级变更,必须登记)

- 旧:cosine 距离,`score 越小越近`,cli.py 输出含"距离"字样;
- 新:RRF 融合分,`score 越大越相关`(两路并集 rank ≥ 1,单路命中 score ≥ 1/(1+60));
- **ROADMAP §7 契约变更登记**,并核对 `tools/rag/cli.py` search 子命令文案;`kb_search` 只透传 score,无需改。

## 7. 常见坑与规避(全优化共享)

| 坑 | 规避 |
|---|---|
| 入库与查询分词不一致 | `tokenize` 唯一模块级函数双端共用;单测强制 |
| 懒重建并发竞态(共享单例 + Send 并行) | `threading.Lock` 双检;重建期间其他线程等锁 |
| score 语义翻转被下游误读 | ROADMAP §7 登记 + cli 文案核对 + 测试断言显式标注"越大越相关" |
| RRF 重排后原 top-1 变化导致断言失败 | 放宽为 top_k 内命中,勿强扭排序 |
| 内存索引规模膨胀(数十万 chunk 百 MB 级) | 接受上限;本项目单机个人库规模远低于阈值;方案 B 为备选 |
| 500 字 chunk 偏长、avgdl 摊薄词频 | BM25Okapi 默认参数即可;勿过度调参,靠评测集说话 |
| 同义词/口语化查询关键词路 miss | 靠向量路兜底(双路互补正是本优化目的);暂不上 LLM 查询改写 |
| rank_bm25 0.2.2 小语料负 idf(高频词占多数时 average_idf<0,epsilon 下限为负,负 idf 词得负分) | `SafeBM25Okapi` 子类覆写 `_calc_idf` 为 +1 平滑标准 BM25 idf(恒非负),"score>0 即有命中词"语义成立 |
